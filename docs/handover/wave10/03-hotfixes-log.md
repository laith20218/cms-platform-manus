## Hotfix 10.8 (63cdb09) — دفعة ميزات ذات طبيعة إصلاحية

- **العرَض**: صف صفحة مشغّل الإنتاج عالقة على حالة «ترميز 720p» بينما الدرجة الفعلية 360p فقط؛ الحلقة العالقة 58% لا سبيل لإلغائها؛ الاختيار `TargetQuality` لا يصل للمُرمِّز.
- **السبب الجذري**: تعيين حالات المراحل بكسور ⅓/⅔ ثابتة على سلّم افتراض ثلاث درجات (المصدر 480p يُسقط 720/1080 فتبقى 360 وحيدة تحمل الحالة الخاطئة)؛ `TargetQuality` كان يُفقد بين initiate والـ encoder؛ لا آلية إلغاء.
- **الإصلاح**: `rungStatuses` من الدرجات **الفعليّة** (N درجات ⇒ N حصص) + تمرير/تخزين `TargetQuality` مع سجل إثبات حي `Starting job: ID, Target, SourceHeight, Rungs` + `abort-processing` (Failed أولًا ثم قتل ffmpeg عبر CTS مرتبط بالمهمة) + مشغّل الطالب المخصص داخل صفحة الكورس.
- **الدرس**: حالة الواجهة يجب أن تُشتق من **نفس** المعطى الذي يبني المحرك (الدرجات الفعلية)، لا من افتراض ثابت.

## Hotfix 10.8c (890236d) — إعداد S3 الصحيح + تنظيف غير معترض

- **العرَض**: `POST .../initiate-upload` يُرجع **500**؛ سجلات Render: بيانات اعتماد Upstash تُسك بنجاح (200) لكن العميل يخاطب `https://smashing-kiwi-127167.upstash.io/` (مضيف وكيل API لا `*.r2.cloudflarestorage.com`) → كل نداء S3 يُجاب **Access Denied**.
- **السبب الجذري**: SDK الرسمي `@upstash/blob` (v0.0.11) يرفض نقطة نهاية لا تطابق `*.r2.cloudflarestorage.com` — الكود C# لم يكن يتحقق من الشكل فمضى صامتًا؛ إضافةً إلى مسار 500 مكشوف (الأخطاء التخزينية كانت تمر خامًا).
- **الإصلاح**: `UpstashS3ClientFactory` يضبط `ServiceURL/ForcePathStyle/AuthenticationRegion` صراحةً من قيمة النهاية المصححة + خريطة 503 ProblemDetails للأخطاء التخزينية + تنظيف غير معترض (لا يُسقط طلب الرفع).
- **الدرس**: عند مزوّد وكيل (Upstash فوق R2) **لا تثق** بنقطة النهاية من واجهة الاعتماد — صادقها نمطًا وثبّتها صراحة.

## Hotfix 10.8d (fd8f50f) — توافق AWS SDK مع R2: فحوص Checksum

- **العرَض**: بعد 10.8c وإعداد `UPSTASH__BLOB__S3ENDPOINT` — لا يزال **503 Access Denied** عند initiate.
- **السبب الجذري** (تشخيص المشرف، وأثبته تحليل الشبكة): ترقية AWSSDK تُزين الطلبات بـ `x-amz-checksum-crc32`/`x-amz-sdk-checksum-algorithm` — تركيبة يرفضها R2. الأدلة المحلية: 3.7.400 لا يرسل شيئًا؛ 3.7.421.10 افتراضيًا (`WHEN_SUPPORTED`) يرسل الترويسات المرفوضة؛ مع `WHEN_REQUIRED` تعود السلكة نظيفة (عدّ برمجي: صفر تطابقات).
- **الإصلاح**: ترقية الحزمة إلى 3.7.421.10 + تثبيت `RequestChecksumCalculation/ResponseChecksumValidation = WHEN_REQUIRED` على **كل** عملاء S3 + سجل تشخيصي كامل عند رفض initiate (الرمز + رسالة المزوّد + ServiceURL).
- **الدرس**: **الترقية وحدها كانت ستُدخِل العلّة** — كل ترقية SDK ضد مزوّد S3-مثل تتطلب فحص سلك (wire-level) قبل الإنتاج. (كُتبت البرهنة بأداة التقاط HTTPS محلية — من خارج المستودع.)

## Hotfix 10.8e (c9d5d0b) — تعطيل توقيع الحمولة (UNSIGNED-PAYLOAD)

- **العرَض**: 403 مستمر عند `InitiateMultipartUploadAsync` رغم 10.8d؛ السجلات تحدد: endpoint صحيح + اعتماد مُسك بنجاح + الفشل عند initiate بالذات.
- **السبب الجذري**: SDK يوقّع الحمولة المتدفقة بترميز SigV4 chunked (`STREAMING-AWS4-HMAC-SHA256-PAYLOAD` + aws-chunked) — R2 يرفضه كعدم تطابق توقيع.
- **الإصلاح** (ببرهنة سلكية): `AmazonS3Config` لا يملك مفتاح `DisablePayloadSigning` على خط 3.7 (مُثبت بالمترجم CS0117 وبـ XML docs — وكذلك v4.0.104.6؛ وحادث `BeforeRequestEvent` متأخر — المارشالر ينسخ قبله). الحل الوحيد الفعّال: **العلم على مستوى الطلب** — `BuildPutObjectRequest()` موقع البناء الوحيد لكل PUT من طرف الـ SDK يثبّت `DisablePayloadSigning=true` → `UNSIGNED-PAYLOAD` بلا إطار aws-chunked.
- **صنفه**: workaround قسري بحدود SDK (لا مفتاح عميل) لكنه **مُوثَّق بالبرهنة السلكية** ومركّز في موقع واحد قابل للتفتيش.
- **الدرس**: وثّق سبب استحالة الحل الأنظف داخل الكود نفسه (فعلنا في doc-comment) كي لا يُعاد اشتقاقه — أو يُكسر — لاحقًا. (ولاحقًا 10.9 أبقاه لـ B2: يقبل الاثنين، والغير موقّع هو الأرخص والأثبت.)

## Hotfix 10.8f (0b3597d) — الرفع بـ Single PUT (تجاوز multipart نهائيًا)

- **العرَض**: سجلات إنتاج + اختبار حي: اعتمادات Upstash المؤقتة **لا تملك صلاحية CreateMultipartUpload على R2** — 403 عند initiate مهما أُصلح السلك.
- **السبب الجذري**: حد مزوّد (صلاحية نطاق الجلسة) — خارج سيطرتنا كليًا.
- **الإصلاح**: هجر multipart للـ Admin API: `GetSignedUploadUrlAsync(fileKey, contentType, 10min, fileSize)` — رابط واحد للملف كاملًا بـ **content-type + الحجم موقّعين**؛ sentinel `UploadId="single-put"` (صفر تغيير schema — كل الحراس القديمة تحتفظ بدلالتها)؛ complete بلا parts مع **إثبات HEAD** (`GetObjectSizeAsync`)؛ الواجهة: XHR واحد مع شريط تقدم `onprogress`، إلغاء فقط (لا استئناف — ذرّية PUT)، إعادة محاولة ضد نفس الرابط.
- **قيود صريحة مقبولة**: عمر الرابط 600s (ملف 2.5GB يحتاج ‎~34Mbps)؛ لا استئناف نقطي؛ شريط واحد.
- **الدرس**: حين يمنع المزوّد نمطًا بنيويًا، **غيّر النمط** إلى ما هو مُثبت لدى المزوّد نفسه (مسار `/v1/presign` الذي يعمل للـ library منذ زمن) بدل ترقيع ما لا يُرقَّع.

## Push 10.9 (2c9f9d0) — الهجرة إلى Backblaze B2 (تحول بنية تحتية)

- **العرَض**: Upstash Blob يبلغ حد الطبقة المجانية **1GB → الحساب قراءة-فقط** — التخزين توقف عمليًا عن الكتابة.
- **السبب الجذري**: نموذج تسعير مزوّد — لا إصلاح كودي ممكن.
- **الإصلاح**: B2 عبر S3 API: `S3StorageService` **المزوّد الوحيد** (حُذف تسجيل Upstash الشرطي كليًا)؛ كل القيم الخمس `Storage:S3:*` fail-closed (كان `BucketName` يسقط صامتًا لـ`cms-files`)؛ `ForcePathStyle=true` **حاسم** لاسم دلو بحالة مختلطة (`CMSmedia`)؛ أبقِي Guards 10.8d/10.8e (B2 يتساهل مع الاثنين). الفئات القديمة بقيت مُصرَّفة (مراجع اختبار/catch) لكن **غير قابلة للتفعيل**. حُذفت متغيرات `Upstash:Blob:*` من Render.
- **البيانات**: لم تُنسخ أي كائنات (لا شيء ذا قيمة في Upstash القراءة-فقط — رفوعات الحادثة لم تكتمل أصلًا).
- **الدرس**: احتراق حد مزوّد مجاني لا يُصلح بترقيع — انقل لمزوّد تملك مفاتيحه (B2)، واجعل الترحيل **تعديل إعداد لا تعديل كود** بفضل تجريد `IFileStorageService`.

## Hotfix 10.10 (b2369ad) — CORS الدلو عبر S3 API عند الإقلاع

- **العرَض**: اختبار إنتاج للرفع إلى B2 يفشل بـ **CORS في المتصفح (status 0)**.
- **السبب الجذري**: واجهة Backblaze **لا تسمح** بضبط `ExposeHeaders: ETag` أو `AllowedHeaders` بنمط wildcard — بينما رفعنا (preflight بـ PUT+Content-Type وقراءة ETag/Content-Range) يحتاجها حرفيًا.
- **الإصلاح**: `S3StorageService.SetBucketCorsAsync()` → `PutCORSConfigurationAsync` (Methods: GET/PUT/HEAD/POST/DELETE · Origins `"*"` · Headers `"*"` · Expose: ETag/Content-Range/Accept-Ranges/Content-Length/Content-Type · MaxAge 3600) — يُستدعى في `Program.cs` بعد `builder.Build()` داخل try-catch (فشل ⇒ تحذير بالرجوع للإجراء اليدوي في `docs/ops/r2-cors.md`، **لا يُسقط الـ API**)، **يتخطى بيئة Testing** (كل مضيفي اختبار التكامل الستة يقلعون بـ `UseEnvironment("Testing")` — لا نداء شبكة في الاختبارات).
- **الدرس**: ما لا تسمح به واجهة مزوّد، **املَه عبر الـ API** — والتطبيق عند الإقلاع idempotent + ذاتيّ الشفاء (كل إعادة نشر تعيد السياسة لو ضاعت من الطرفية).
- **ملاحظة SDK**: اسم الخاصية الحقيقي `CORSRule.MaxAgeSeconds` (لا `MaxAgeInSeconds` الذي لا وجود له في 3.7.421.10).

## Hotfix 10.12 (d055c4d) — CSP لنطاق B2 (إصلاح blocked:csp)

- **العرَض**: مشغّل الطالب عالق على «جاري تجديد الرابط…»؛ تبويب الشبكة: طلبات `master.m3u8` تُجاب **`(blocked:csp)`**.
- **السبب الجذري**: CSP على Vercel ما زال يذكر المزوّدين المتقاعدين (R2) ولا يشمل `*.backblazeb2.com` — **hls.js يجلب القوائم والمقاطع عبر XHR ⇒ التوجيه الحاجب هو `connect-src`**.
- **الإصلاح**: إضافة `https://*.backblazeb2.com` إلى `connect-src` (الحاسم) + `media-src` + `img-src` + `frame-src` في `apps/student-web/vercel.json`، مع **حذف R2 الميت** من frame-src؛ وإضافة كتلة ترويسات أمنية كاملة + CSP **مطابقة بايت-ببايت** إلى `apps/admin-web/vercel.json` (لم يكن لديه أي CSP قبلها!).
- **الدرس**: **CORS (خادم) و CSP (متصفح) نصفان لسياسة واحدة** — كل هجرة مزوّد يجب أن تحركهما معًا (هذا ما فات 10.9). وتحقق من الواجهة الثانية أيضًا عند تعديل سياسة أمنية مشتركة.

## Hotfix 10.13 (17754a1) — خطوط CSP + تشخيص 401

- **العرَض (أ)**: خطوط Google محجوبة CSP؛ **(ب)**: `master.m3u8` يُجاب **HTTP 401** والمشغّل عالق على «تجديد الرابط…».
- **السبب الجذري (أ)**: كلا التطبيقين يستورد CSS الخطوط من `fonts.googleapis.com` في `globals.css` — استيراد ورقة أنماط يحكمه **`style-src`** الذي لم يكن يشمل الأصل (بينما `font-src` يشمل `fonts.gstatic.com` منذ البداية — الحجب كان في التوجيه الخطأ من التشخيص الأولي!).
- **الإصلاح (أ)**: `style-src` += `https://fonts.googleapis.com` في التطبيقين. *(قيد التأكيد الحي في الإنتاج بعد النشر.)*
- **ب (تشخيص، الحل الكامل معلَّق — وثيقة 04 §1)**: أُضيفت سجلات تشخيصية **مؤقتة**:
  - `S3StorageService.GetSignedUrlAsync` → `Presigned GET issued: ServiceURL=… Bucket=… Key=… ExpiresIn=…s Url=<REDACTED>` — يقنّع `X-Amz-Signature` فقط؛ **keyID يبقى مرئيًا عمدًا** (دليل المفتاح الموقِّع).
  - `VideoTranscodingService` → بدء المهمة عند الالتقاط + **سبب التخطي** (كان صامتًا!) + الإكمال مع `HlsKey` الدقيق.
  - وتحقّق شامل: `processingStatus` يصل الواجهة (DTO منذ 10.5) وبوابة المشغّل تعمل (بطاقة مقفلة منذ 10.8) — لا تغيير لازماً.
- **الدرس**: «الحجب» يحتاج تحديد **التوجيه** الصحيح (style مقابل font) — والمُوقِّع المحلي لا يتحقق من الوجود؛ 401 من دلو خاص يعني غالبًا كائنًا غير موجود **أو طلبًا غير موقّع** (وهو جوهر القضية المفتوحة).

## الأنماط المتكررة عبر السلسلة (خلاصة للجلسة القادمة)

1. **سلسلة 10.8c–f كلها سببها واحد: مزوّد Upstash فوق R2** — أصلحنا السلك ثم الترميز ثم الصلاحيات، والمحصلة: هجر النمط كليًا. **دعّسنا 4 إصلاحات على مزوّد كان يجب هجره من الأول** — حين تتوالى 403/401s غامضة من مزوّد وكيل، شخّص **الصلاحية/النطاق** أولًا لا الترميز.
2. **كل "إصلاح تحته مزوّد" يجب أن يتحرك على ثلاث طبقات معًا**: كود العميل (توافق SDK) + سياسة الدلو (CORS) + سياسة المتصفح (CSP). 10.9 حرّك الأولى فقط؛ 10.10 و10.12 كانتا ردم الفجوتين.
3. **سجلات البرهنة قبل الإصلاح** (10.8d/10.8e: أدوات التقاط سلك؛ 10.13: presign/skip logs) هي التي جعلت كل خطوة قابلة للتحقق — لا تنشر إصلاحًا بلا سطر سجل يثبت نجاحه.
